# Migrate from Starlight

Starlight stores documentation in Astro content collections and uses standard Markdown or MDX, so
the Astro-to-Astro path is especially direct. The key work is translating sidebar configuration,
Starlight components, expressive code options, and integration behavior.

<Callout type="tip" title="Astro is the shortest target">
  If you want to keep the existing Astro application, initialize the Farming Labs Astro adapter and
  migrate only the docs integration and content wiring.
</Callout>

<Agent>
Read the starlight() integration options in astro.config and resolve every sidebar item, autogenerate
directory, locale, plugin, and component override. Do not copy Starlight config keys into
docs.config without mapping their behavior.
</Agent>

## 1. Inventory the source

Collect:

- `astro.config.*` and the `starlight(...)` integration
- `src/content/docs/` Markdown and MDX
- `src/content.config.*` or `src/content/config.*`
- manual and autogenerated sidebar definitions
- `src/components/` and Starlight component overrides
- `src/styles/`, `public/`, logos, favicons, and social images
- plugins, expressive code config, locales, redirects, search, and custom head tags

## 2. Map the files

| Starlight | Farming Labs Docs |
| --- | --- |
| `src/content/docs/**` | Target `contentDir`, commonly `docs/**` for Astro |
| `starlight({ sidebar })` | Directory hierarchy and page `order` |
| Starlight `title`, `description`, and social config | `docs.config.ts` metadata and theme |
| component overrides | Theme config or registered Astro/MDX components |
| `src/styles/**` | Global CSS or theme overrides |
| `public/**` | Existing Astro `public/**` |
| Starlight plugins | Farming Labs feature config or explicit Astro integration |

Keep the existing Astro application when it contains non-doc routes; replace only the Starlight
docs integration and route surface.

## 3. Preserve routes and frontmatter

Starlight normally derives docs routes from files under `src/content/docs`. Preserve directory and
filename slugs, then review:

- `title`
- `description`
- `slug`
- `sidebar`
- `tableOfContents`
- `template`
- `hero`
- `banner`
- edit and pagination settings

Portable title and description fields can remain. Translate layout, hero, banner, and sidebar
objects into Farming Labs page content, theme configuration, or application UI.

## 4. Translate sidebar configuration

Starlight supports link items, groups, badges, translations, and autogenerated directories.

1. Snapshot the fully resolved sidebar.
2. Turn groups into directories with landing pages when useful.
3. Add numeric `order` values matching manual item order.
4. Expand autogenerated directories into their actual page list.
5. Preserve external links through custom navigation.
6. Recreate labels and badges with stable text and registered icons.

Do not lose pages excluded from autogeneration; classify them as hidden, redirected, or retired.

## 5. Convert authoring features

| Starlight pattern | Target |
| --- | --- |
| `:::note`, `:::tip`, `:::caution`, `:::danger` | Supported directive or `<Callout>` |
| `<Tabs>` and `<TabItem>` | Built-in `<Tabs>` and `<Tab>` |
| `<Card>` and `<CardGrid>` | Built-in cards or a registered component |
| `<Steps>` | Ordered headings/list or a registered component |
| expressive-code mark/insert/delete metadata | Supported code fence metadata |
| Starlight icon names | Farming Labs icon registry |
| Astro component import | Keep for Astro or rewrite for another runtime |

Standard Markdown, headings, tables, links, and fenced code should remain unchanged.

## 6. Replace integration behavior

Map Starlight integration options intentionally:

- metadata and social images → `metadata` and `og`
- search → `search`
- edit links and page actions → `github` and `pageActions`
- locales → Farming Labs locale configuration
- custom CSS → theme overrides and global CSS
- component overrides → theme config or registered components
- plugins → built-in feature config or a separate Astro integration

## 7. Validate and recover

1. Run the Astro production build.
2. Compare all `src/content/docs` routes and manual sidebar links.
3. Test autogenerated groups, badges, callouts, tabs, cards, and expressive code.
4. Inspect locale navigation and base paths.
5. Verify assets and application routes outside docs.
6. Fetch representative pages through `.md`.

If navigation is incomplete, compare the resolved Starlight sidebar with the target tree. If an
Astro component fails after changing runtime, replace it with portable Markdown or a native target
component.
